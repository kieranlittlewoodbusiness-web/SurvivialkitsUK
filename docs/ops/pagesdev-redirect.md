# Redirect uksurvivalkits.pages.dev to the apex

The Cloudflare Pages production alias `https://uksurvivalkits.pages.dev` should return a **301** to the apex `https://uksurvivalkits.uk`, keeping the path and query string. Preview and branch aliases must not be redirected, because QA uses them.

This cannot be done in the repo with Pages `_redirects`. Apply the Bulk Redirect below in the Cloudflare dashboard (K55).

## Applied

On 16 November 2026 at 19:08 Europe/London, `curl -sI` returned a 301 from `https://uksurvivalkits.pages.dev/` to `https://uksurvivalkits.uk/`, and from `/checklist/?x=1` to `https://uksurvivalkits.uk/checklist/?x=1`, while the apex, a branch preview and a versioned alias returned 200 ([evidence on #33](https://github.com/kieranlittlewoodbusiness-web/SurvivialkitsUK/pull/33#issuecomment-6926295424)). The plain `http://` check was not run: the network used for the check can't make plain HTTP requests.

## Why not `_redirects` or a Pages Function

Pages `_redirects` cannot match on host. The source of each rule is a file path, and [domain-level redirects are unsupported](https://developers.cloudflare.com/pages/configuration/redirects/):

> Domain-level redirects ❌ — `workers.example.com/* workers.example.com/blog/:splat 301`

A path-only rule such as `/* https://uksurvivalkits.uk/:splat 301` would also send the apex and every preview alias (`<hash>.uksurvivalkits.pages.dev`, `<branch>.uksurvivalkits.pages.dev`) to the apex, which would break QA.

A Pages Function `_middleware` could inspect the host and call `next()` otherwise, and that would be a repo change. It is the worse option here:

- Cloudflare’s own guidance for this exact case is account-level [Bulk Redirects](https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/), also described under [Disable access to `*.pages.dev`](https://developers.cloudflare.com/pages/configuration/custom-domains/#disable-access-to-pagesdev-subdomain).
- A root `functions/_middleware.js` runs on every request, including the apex and preview aliases, and adds a Workers invocation to each one. This site is static and has no Functions today.
- [`_headers` are not applied to responses generated by Pages Functions](https://developers.cloudflare.com/pages/configuration/headers/), even when the URL matches a header rule. That would put the existing production-alias and preview `X-Robots-Tag: noindex` rules, and the `/*` security headers, at risk unless they were re-implemented in the Function.

Bulk Redirects run in front of the Pages project, so `_headers` on the apex and on preview aliases are unchanged. After the 301, the production alias itself will no longer serve a 200 with noindex; crawlers are sent to the indexable apex, which is the point of the redirect.

## Exact rule (Bulk Redirects)

Bulk Redirects are [account-level](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/create-dashboard/) and available on every plan, including Free (15 rules, 5 lists, 10,000 redirects). They can match `*.pages.dev` hosts; a zone Single Redirect on `uksurvivalkits.uk` cannot, because that hostname is on a different zone. Lists and rules created from a zone’s **Rules → Settings → Bulk Redirects** tab are still account-level.

**Do not turn on Include subdomains.** The [official pages.dev how-to](https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/) enables it, which would also redirect `<hash>.uksurvivalkits.pages.dev` and `<branch>.uksurvivalkits.pages.dev`. Include subdomains is off by default; leave it off so only the exact host `uksurvivalkits.pages.dev` matches.

### 1. Create a Bulk Redirect List

In the Cloudflare dashboard, go to **Bulk redirects** (account level), or **Workers & Pages** → this Pages project → **Bulk Redirects**.

- **List name:** `pagesdev_to_apex` (or similar; must be unique on the account)
- **Description:** `301 uksurvivalkits.pages.dev to https://uksurvivalkits.uk, exact host only`

Add one URL redirect. Expand **Edit parameters** and set the flags below; the two default-off flags that must be on (Preserve query string and Subpath matching) are easy to miss.

| Field | Value |
| --- | --- |
| **Source URL** | `uksurvivalkits.pages.dev` |
| **Target URL** | `https://uksurvivalkits.uk` |
| **Status** | `301` |
| **Preserve query string** | **On** (API: `preserve_query_string: true`; default is off) |
| **Subpath matching** | **On** (API: `subpath_matching: true`; default is off) |
| **Preserve path suffix** | **On** (API: `preserve_path_suffix: true`; default is on) |
| **Include subdomains** | **Off** (API: `include_subdomains: false`; default is off — do not enable) |

A source URL with no scheme matches both `http` and `https`. A source URL cannot include a query string; **Preserve query string** is what keeps `?utm=…` and similar parameters.

With those parameters, `https://uksurvivalkits.pages.dev/start-here/?ref=test` becomes `https://uksurvivalkits.uk/start-here/?ref=test`. `https://<hash>.uksurvivalkits.pages.dev/` and `https://<branch>.uksurvivalkits.pages.dev/` are not matched.

Do not add a DNS record for `uksurvivalkits.pages.dev` on the `uksurvivalkits.uk` zone. That hostname is already served by Pages. If the dashboard prompts to create a proxied DNS record for the source hostname, skip it.

### 2. Create a Bulk Redirect Rule

- **Rule name:** `pages.dev production alias to apex`
- Select the list created above
- **Save and Deploy**

Equivalent list-item parameters (for the API or a later Terraform import):

```json
{
  "source_url": "uksurvivalkits.pages.dev",
  "target_url": "https://uksurvivalkits.uk",
  "status_code": 301,
  "preserve_query_string": true,
  "subpath_matching": true,
  "preserve_path_suffix": true,
  "include_subdomains": false
}
```

## Post-apply curl checks

Run these from a network that can reach the public site. Expect a single `301` hop from the production alias onto the apex, with the path and query preserved, and **no** redirect from a preview or branch alias.

```sh
curl -sI https://uksurvivalkits.pages.dev/
# HTTP/2 301
# location: https://uksurvivalkits.uk/

curl -sI https://uksurvivalkits.pages.dev/start-here/?ref=test
# HTTP/2 301
# location: https://uksurvivalkits.uk/start-here/?ref=test

curl -sI https://uksurvivalkits.pages.dev/compare/72-hour-emergency-kits/
# HTTP/2 301
# location: https://uksurvivalkits.uk/compare/72-hour-emergency-kits/

curl -sI -L https://uksurvivalkits.pages.dev/start-here/
# Final response: HTTP/2 200 on https://uksurvivalkits.uk/start-here/

curl -sI https://uksurvivalkits.uk/
# Still HTTP/2 200 (the apex must not redirect)

# Replace with a real preview or branch alias. Must stay 200, not 301 to the apex.
curl -sI "https://<deployment-id>.uksurvivalkits.pages.dev/"
# HTTP/2 200
# x-robots-tag: noindex
```

Also confirm the apex still has no `x-robots-tag: noindex`.
